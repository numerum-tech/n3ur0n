## Key Learnings

- **Bootstrap vs gateway in code:** peer SQLite directory = Gateways UI; `bootstrap.toml` / env / CLI = cold-start seed URL list. Manual Add merges into both. Detail: unseed via `POST /settings/bootstrap/remove`; delete gateway via `DELETE /peers/:id`. Transitive discoveries stay in peer DB only. `openPeerInspector` must refresh `/peers` if `_peersCache` is empty (Gateways opens detail without Network load).
- **Project:** N3UR0N
- Cap hot-reload requires the server to run in manifest mode (`--manifest-dir` flag or `N3UR0N_MANIFEST_DIR` env). Without it, `Node::reload_caps_from_manifest_dir()` returns `node was not built in manifest mode — cap hot-reload unavailable`.
- TOML basic strings (`"..."`) cannot contain literal `\n`/`\r`/`\t`. When generating TOML from JSON values in `crates/server/src/settings.rs`, always escape these chars in both `toml_str` and `json_to_toml_value`.
- Cap binding kinds map 1:1 to backend kinds at runtime: `prompt` → `openai_compat`, `http` → `http_base`, `mcp` → `mcp_server`. UI filters backend dropdown by selected binding kind.
- `AccessMode` has 3 variants: `Free` (wire `"free"`, UI "Public"), `Restricted`, `Private`. Private caps MUST be filtered out of `describe_self` (use `registry.public_decls()`), rejected as `UnknownCapability` in inbound `invoke` to avoid existence disclosure, and excluded from peer-directory `get_known_peers` capability filter. Local API (`/api/v0/caps`) + local planner still see them. Wire literal stays `"free"` (no rename) for v0.1 backward compat.
- Backend hot-reload: `Node.backends` is `Option<Arc<ArcSwap<BackendsRegistry>>>`. Call `Node::reload_backends_from_manifest_dir()` to swap; it automatically triggers `reload_caps_from_manifest_dir()` so cap bindings rebuild against the new backend instances. Pre-existing in-flight invokes keep the old Arc<HttpBackend> etc and run to completion.
- i18n architecture (UI): catalogs live at `crates/server/ui/locales/<code>.json` flat key→string maps with a `_meta` block (code, name, native_name). Embedded into the binary via rust-embed. `/api/v0/locales` enumerates available catalogs at runtime by scanning embedded asset paths starting with `locales/`. Frontend `ui/i18n.js` exposes `t(key, params)`, `setLocale(code)`, `listLocales()`. Static HTML uses `data-i18n="key"` + `data-i18n-attr-<name>="key"` for attributes. Dynamic render paths call `t()` and re-render on the `n3ur0n:locale-changed` event. Adding a language = drop new JSON file + rebuild. `app.js` is loaded as `type="module"` since i18n.js uses ES exports.
- RBAC architecture: 3 roles (`user`, `operator`, `admin`) stored in `users.role` (SQLite migration `0003`). Permissions are role→`&'static [&'static str]` map in `crates/server/src/auth.rs` (`permissions_for(role)`). Wire enforcement: `session_middleware` reads `n3ur0n_session` cookie → injects `AuthedUser` extension → `require_authed` 401s missing extension → `require_perm!(perm::X)` macro 403s missing permission. UI cosmetic gating via `data-perm="key"` attributes + `auth.applyPermDom()`. Bootstrap flow: first launch with zero users → `/api/v0/auth/me` returns `bootstrap_required: true` → UI shows bootstrap form → `POST /auth/bootstrap` creates first Admin and issues session. Dev bypass: `N3UR0N_AUTH_DISABLE=1` env injects synthetic admin (loopback only). Routes-without-/api/v0-prefix pattern: `auth::router()` and `settings::router()` emit prefix-less routes, `http::app_with_settings()` nests them under `/api/v0` so the session middleware stack covers everything.

- `OpenAIBackend::build_request` verrouille `model` au `default_model` opérateur quoi que le caller envoie (anti-hallucination de noms de modèles par le compile). Le doc-comment de `OpenAIConfig.default_model` (« Overridable in each invoke payload ») est faux. Tout feature nécessitant un override de modèle doit passer par le flag opt-in `allow_model_override` (cf. spec n3ur0n-direct-chat-v0.md §3.3) — ne jamais relâcher le verrou pour les backends exposés au réseau.
- Le LLM du planner est une config dédiée (`--planner-llm-*` / `N3UR0N_PLANNER_LLM_*`), totalement disjointe des backends exposés par l'instance. Le doc-comment CLI de `--planner-llm-base-url` (« defaults to the chat backend's URL ») est obsolète : le flag est requis.

- **UI stack (verified 2026-07-28, both modes at runtime):** there is NO frontend framework and NO JS build step in this project. The web UI is `crates/server/ui/` — hand-written vanilla JS ES modules + CSS (~4.3k LOC, `app.js` alone is 3500). One codebase, two shells: the **server** embeds it via rust-embed `#[folder = "ui/"]` ([http.rs](crates/server/src/http.rs)); the **desktop** points its Tauri window at `WebviewUrl::External("http://127.0.0.1:<port>/ui/")` served by its own embedded axum ([desktop/src/main.rs:273](crates/desktop/src/main.rs#L273)) — so `frontendDist: "../server/ui"` in `tauri.conf.json` just satisfies tauri-build; the window never loads from disk-bundled assets. Proven by running the docker image (which contains no `frontend/` at all) and getting 200s on `/ui/{index,app.js,auth.js,i18n.js,icons.js,style.css,locales/*}`.
- **Dev loop for UI:** rust-embed is used WITHOUT the `debug-embed` feature, so debug builds re-read `crates/server/ui/` from disk on every request. Edit a `.js`/`.css` → reload the page → done, no recompile. Release builds embed. (Verified by appending a marker to `icons.js` against a running debug server and re-fetching.)
- **Desktop has no package.json and no pnpm.** Dev = `cargo run -p n3ur0n-desktop`. Bundles need `cargo install tauri-cli@^2` then `cargo tauri build`. CI uses `tauri-apps/tauri-action` with `projectPath: crates/desktop`. Any doc saying `pnpm tauri dev` or `pnpm --filter frontend …` is wrong — there was never a root pnpm workspace to filter from.

- **Planner model choice is the single biggest accuracy lever (measured 2026-07-29, 3 runs × 22 cases each).** `qwen2.5:7b` = 100% tool-exact, all categories 100%. `llama3.1:8b` = 86%, with the abstention categories at none 83% / trap 50% — i.e. it over-plans. `qwen2.5:3b` 68%, `llama3.2:3b` 50%, `qwen2.5:0.5b` 41%. **7B is the practical floor; the 3B→7B cliff holds across families.** `llama3.1:8b` is still the default in `docker/compose.yml` (`PLANNER_MODEL`) and in the docs — switch it. Re-run with `scripts/planner-eval.sh <model> <runs>`; reports land in `target/bakeoff/` and there is a comparison-table script pattern in the session scratchpad.
- **Over-planning is the planner's dominant failure mode, and it is model-driven, not prompt-driven.** With llama3.1:8b the live cluster answered "What is 17 plus 25?" with a 2-step `[random_int, chat]` plan and an incoherent reply; qwen2.5:7b returns 0 steps and "42". Prompt rewording did *not* fix it (a reasoned retry-prompt reorder changed nothing on the case it targeted). Do not spend effort on prompt polish for this class of bug before checking the model.
- **The corrective retry (`resolve_plan` in `planner/plan_exec.rs`) only pays off on a model that already clears the gate.** qwen2.5:7b: 3 retries, 3 recoveries, no downside. qwen2.5:0.5b: 27 retries, **0** recoveries — pure wasted latency. On llama3.1:8b its one observed effect was rescuing an over-planned `none` case into executing a tool it should not have. It is not a fix for an undersized model.
- **`validate_plan` reports an empty plan as an error** (`"plan has no steps"`). Any code validating before checking `plan.is_empty()` treats every legitimate no-tool answer as a failure. `dispatch_inner` had exactly that ordering bug, which also made its `is_empty` branch dead code.

- **Cap authoring: positive examples do the work, negative examples are weak.** Measured 2026-07-29: `search_unknown_url` failed deterministically (picked `fetch_url` over `web_search`) even though `fetch_url` carried a `negative_example` repeating that exact intent almost verbatim. Adding **one** positive example to `web_search` fixed it. Rule: cover the phrasings you want to win with positive examples on the *right* cap; do not rely on a counter-example attached to the wrong one.
- **Example authoring has NON-LOCAL effects.** That same one-example addition to `web_search` flipped two unrelated cases (`rewrite_not_translate`, `fetch_known_url`), net 98% → 95%. Never tune one cap's examples in isolation — re-run `scripts/planner-eval.sh` after any change. Operationally serious: independent publishers editing their own caps perturb each other's selection.
- **The compile prompt hardcodes "translation / summary / arithmetic → empty plan" regardless of catalog.** That rule is wrong the moment a dedicated `translate` or `summarize` cap exists — the model correctly ignores it and the eval then scores the *correct* behaviour as a failure. Known prompt bug in `default_compile_system_prompt` (`planner/plan_exec.rs`): the rule needs to be conditional on whether a matching cap is in the catalog.
- **Eval catalog difficulty is a first-class knob.** `crates/node/tests/fixtures/planner_caps.json` adds 9 overlapping caps across 5 peers on top of the 4 real `UtilityBackend` caps; `PLANNER_EVAL_CATALOG=basic` restores the trivial catalog. Distractors alone dropped qwen2.5:7b's `none` category from 100% to 75% — over-planning scales with catalog richness, so a suite with a trivial catalog will not predict live behaviour.

- **NEGATIVE RESULT — do not add a BM25 relevance floor to the planner catalog.** Tried 2026-07-30 (drop caps scoring below 25% of the top score), measured, reverted. With a lexical retriever a floor converts a *ranking* weakness into **silent capability loss**: `"…then summarise what you find"` scores `summarize` at rel 0.17 (pruned) while `"…summarize…"` scores rel 0.49 (kept) — one letter decides whether the cap exists, and it regressed the `chain` category 100%→86%. Separately, `"Quelle heure est-il maintenant ?"` scores **0.000 on every English cap**, so on this EN/FR product a floor would routinely empty the catalog. Ranking + a bound is safe (a cap only drops when another outranks it); an absolute cut is not. Revisit **only after** semantic/hybrid retrieval exists. The reasoning is preserved as a comment block in `planner/catalog.rs`.
- **Prompt ORDER is load-bearing, not just prompt content.** Sorting the catalog unconditionally (rather than only when it must be trimmed) broke an unrelated `chain` case — `reverse` emitted without its required `text` arg — purely because skills moved position. Third instance of the non-locality effect. Only reorder when you actually have to drop something; it also keeps upstream prefix caches warm.
- **`Catalog::filter_for_query` is the shared filter** used by both `build_for_query` (runtime) and the eval suite. Keep it that way: before it was extracted, the eval graded an unfiltered catalog — a code path no user ever hits.

### Decision 2026-07-28 — registry-as-capability is discovery time, not plan time
- **Chosen: model A (discovery time).** Registry consulted outside dispatch (bootstrap / schedule / explicit user action) → results ingested into the `peers` table → next dispatch's catalog picks them up. `plan_exec` untouched.
- **Why plan time is impossible as a plan step:** `validate_plan` ([planner/plan.rs](crates/node/src/planner/plan.rs), ~line 116) hard-rejects any step whose tool is missing from the catalog snapshot built *before* compile ([plan_exec.rs](crates/node/src/planner/plan_exec.rs), ~line 156). A `registry.search` step would run, and nothing downstream in the same plan could invoke what it found. Plan time therefore requires a full recompile (3 LLM calls/message), which was deferred.
- **Ingestion path:** `search result → discovery::refresh_peer() → peers table`. `refresh_peer` already fetches `describe_self` from the peer and verifies it, so the registry returns *pointers, never authority* — a lying registry cannot forge a cap (`client::send_signed` verifies signature + recipient + sender match).
- **Constraint to remember:** `Catalog::build` skips any cap with `examples.is_empty()` (both local and remote). Indexed peers stay invisible to planners unless their `CapabilityDecl` carries ≥1 example.
- **Registry side needs no new binding kind:** implement `registry.search`/`registry.announce` via the existing `http` (or `mcp`) binding pointing at a small indexer service. Zero core/protocol change. A native binding is only worth it if registry becomes first-class.
- Deferred alternatives: prefetch on weak BM25 match (1 compile, reduced query leak) — likely next; plan-time recompile — must earn its third LLM call with miss-rate data.

### Learning 2026-06-26 — node crate fmt/clippy drift (env)
- `cargo fmt -p <crate>` formats the WHOLE crate, ignores file-path args. To format one file only: `rustfmt --edition 2024 <file>`.
- `crates/node` has pre-existing rustfmt drift (import ordering, string-continuation indent) and `crates/adapters/src/openai.rs` + `plan_exec.rs` trip newer clippy collapsible-if / let-chain lints. These predate P2 work — do NOT fold them into a focused feature commit. Verify a single file with `rustfmt --check <file>`.
